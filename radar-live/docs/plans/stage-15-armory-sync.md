# Stage 15: armory-sync (nightly character ingest from the WoW Forever armory)

STATUS: PLAN ONLY. Nothing here has been implemented. Written 2026-11-12.
Supersedes the design in `stage-10-armory.md` (per-contact lookups inside radar-ingest, OAuth client id/secret). Stage 10's
profile *page* work (A5 / U6 tooltip rows) is still wanted and consumes the data this stage stores.

## 1. Goal
A scheduled, standalone process, `radar-armory`, that once a day at 00:00 walks **every character the WoW Forever armory
exposes** (not only contacts seen in combat logs) and stores key details: level, class/race/faction, guild, gear, talents,
health, mana (or other power), PvP progress, plus whatever else the API offers. It is separate from the website
(radar-db's public listener, `site/`) and from radar-ingest, but it can reach the database.

## 2. Decisions (recommended; confirm the starred ones)
| # | Decision | Why |
|---|---|---|
| D1 | New binary `cmd/radar-armory`, own systemd service + **timer** (`OnCalendar=*-*-* 00:00:00`, `Persistent=true`, `RandomizedDelaySec=0`). One-shot process per run, not a long-lived daemon. | Matches "once a day, separate process". The timer replaces an in-process scheduler, restarts need no state, `Persistent=true` catches a missed midnight after the laptop was off. |
| D2* | **DB access goes through radar-db's internal listener** (new `POST /internal/v1/armory/batch`, ingest-role key, loopback only), not by opening the SQLite file. | `sqlstore` takes an exclusive `<db>.lock` and has a single-writer design (`internal/mod/sqlstore/lock.go`, `guard.go`); a second process writing the file breaks both. The internal API keeps schema, validation, integrity checks, disk-full 507 and backups in one place, exactly like radar-ingest's relay today. Rejected alternative: direct multi-process SQLite (needs lock redesign, WAL tuning, duplicate validation). |
| D3 | Env var `WOW_ARMORY_API_KEY` is the only secret, read once at start, held in a `core.Secret` (prints `<redacted>`), never in flags, logs, metrics, audit or error text. | User requirement. Note: this name deviates from the `RADAR_*` rule in `docs/security/secrets-policy.md`; update that file with an explicit exception for this one name. Also support `WOW_ARMORY_API_KEY_FILE` (path to a 0640 root:radar file, loaded via systemd `LoadCredential=`/`EnvironmentFile`) so the value need not sit in `radar.env`. The plain env var wins if both are set. |
| D4 | Midnight = **server local time** by default; `RADAR_ARMORY_TZ`-style override is not offered (systemd `OnCalendar` honours the host zone; document it). Stored times stay UTC epoch ms (project rule). | Project rule 5. |
| D5 | Snapshots are **upserted current state plus a small history**: `armory_characters` (latest) and `armory_snapshots` (one row per character per day, compact JSON of gear/talents, pruned after N days, default 30). | History enables "gear changed", PvP progress deltas; cap keeps SQLite small on a weak laptop. |
| D6 | Per-ruleset: armory rows are keyed by `(realm, character_name)` with an optional link to `contacts(rs, guid)` by realm+name match. | Armory has no combat-log GUIDs. |

## 3. Gate: Task R0, armory API discovery (blocks everything)
`WOW_ARMORY_API_KEY` implies a single API key, not Stage 10's OAuth pair, but **nothing is known about the API**: a web search found no
public WoW Forever armory documentation. The user must supply the official docs URL (or sample requests) so R0 can write
`docs/plans/armory-api-notes.md` answering, with synthetic samples only:
1. Base URL, auth scheme (header name / query param / bearer), key quota and terms of use.
2. **How to enumerate all characters.** This decides the whole crawl design. Candidate shapes: a paginated "list characters" endpoint;
   per-realm or per-guild lists; a leaderboard/ladder; or no enumeration at all (then we can only refresh names we already know:
   contacts from logs plus guild rosters, and "all characters" is not achievable, which the user must be told).
3. The character detail endpoint(s): which return gear, talents, stats (health, mana), level, PvP (rating, honor, kills, arena/BG
   brackets, titles), guild.
4. Rate limits (per second/minute/day), pagination limits, caching headers, error codes, what "not found/hidden/inactive" looks like.
5. Whether the key may be used from a server (vs. browser-only) and whether data may be stored/redisplayed.
Output includes the final field list for section 5, so the schema is frozen only after R0.

## 4. Architecture
```
systemd timer (00:00) -> radar-armory (one run, exits)
  config/secret -> armory client -> crawler (enumerate -> detail fetch, rate-limited, resumable)
      -> mapper (API JSON -> domain.ArmoryCharacter, sanitised/clamped) -> batcher (<=100 chars)
      -> dbclient (HTTPS-less loopback, ingest key) -> radar-db internal /internal/v1/armory/batch
           -> writeapi (validate) -> core.ArmoryStore (optional iface) -> sqlstore / memstore
radar-db readapi: GET /api/v1/armory/character?realm=&name=, /api/v1/armory/characters?realm=&guids|names= (view key, rate-limited)
```
New code layout (modular, removable like the other modules; nothing outside `cmd/radar-armory` imports the client):
- `internal/domain/armory.go`: `ArmoryCharacter`, `ArmoryBatch`, validation/sanitising (reuses `domain/text.go`).
- `internal/core/store.go`: optional `ArmoryStore` interface (hosts without it return 404 for armory routes).
- `internal/mod/armoryclient`: pure HTTP client + mapper (no host, no DB).
- `internal/mod/armorysync`: crawler, checkpoint, batcher, run summary. Pure, depends on small interfaces (`Source`, `Sink`, `Clock`).
- `internal/mod/writeapi`: add the batch route. `internal/mod/readapi`: add read routes. `internal/mod/sqlstore` and `memstore`: store impl.
- `cmd/radar-armory`: main, flags, module list, exit codes. `deploy/radar-armory.service` and `radar-armory.timer`.
- Architecture test: `armorysync` must not import `sqlstore`; only `cmd/*/modules.go` imports `internal/mod/*` (existing rule).

## 5. Data model (final fields after R0; schema migration v2 in sqlstore)
```
armory_characters (realm TEXT, name_lc TEXT, name TEXT, guid_link TEXT NULL,
  class TEXT, race TEXT, faction TEXT, level INTEGER, guild TEXT,
  health INTEGER, power_type TEXT, power INTEGER,       -- "health and mana": max values as reported
  gear TEXT,        -- JSON: slot -> {itemId, name, ilvl/quality, enchants, gems}  (size-capped)
  talents TEXT,     -- JSON: spec/tree points + selected talents (size-capped)
  stats TEXT,       -- JSON: other core stats (AP, SP, armor, crit...) if offered
  pvp TEXT,         -- JSON: rating(s), honor, kills, arena/BG brackets, title
  api_updated_at INTEGER NULL, fetched_at INTEGER NOT NULL, status TEXT,   -- ok | hidden | notfound | error
  PRIMARY KEY (realm, name_lc)) WITHOUT ROWID;
armory_snapshots (realm, name_lc, day INTEGER, gear_hash TEXT, level INTEGER, pvp TEXT, ... PRIMARY KEY (realm, name_lc, day));
armory_runs (id, started_at, finished_at, enumerated, fetched, stored, skipped, failed, status)   -- observability, "last good run"
```
Indexes: `(realm, class)`, `(guild)`, `(fetched_at)`. JSON columns are validated for size and shape in `domain`, never string-built SQL (existing
`sqlinject_test` pattern). Pruning of snapshots goes through the existing `prune.go` mechanism.

## 6. Crawl behaviour (the "trickle")
- Runs at 00:00; the whole job has a **wall-clock budget** (default 6 h) and a **request budget** (from R0's quota) so it cannot overrun into
  the day or burn the key.
- **Token-bucket limiter** sized below the documented rate limit, concurrency cap (default 2-4), exponential backoff with jitter, honours
  `Retry-After`; 429/5xx trip a **circuit breaker** (open for a cool-down, then resume).
- **Resumable checkpoint**: after each batch the crawler records its cursor (realm/page/last name) in `armory_runs` through the DB API; a crashed
  or interrupted run resumes the same night instead of restarting. Fetches are idempotent (upsert by `(realm, name_lc)`; replay is a no-op).
- **Delta-aware**: skip a character whose `api_updated_at` (or `ETag`/`Last-Modified`) is unchanged, to save quota.
- Batches of <=100 characters, each retried independently; one poison character (bad JSON) is counted and skipped, never aborts the run.
- Exit codes: 0 ok, 1 partial (some failed), 2 fatal (auth 401/403, config); the unit's `OnFailure=` hook reuses the existing alert hook.
- SIGTERM stops gracefully after the in-flight batch.

## 7. Security (character names and API JSON are untrusted)
- Key only via `WOW_ARMORY_API_KEY` / `_FILE`; redaction tests (error strings, logs, `%v` of config, panic path) as in `core/secret_test.go`; repo
  secret-scan rule updated; add to `docs/security/secrets-policy.md` and the checklist (new SEC rows).
- Outbound: fixed HTTPS host from config (validated https, no userinfo), **no redirects**, TLS verified, response size cap, timeouts, path
  segments URL-escaped, names never build a host. systemd `IPAddressAllow=` for the API host plus loopback if ranges are stable.
- Inbound to radar-db: ingest-role key (`RADAR_ARMORY_DB_KEY`, env only), internal listener only, strict `internal/validate` limits, size caps
  on every JSON blob, 507 disk-full behaviour inherited.
- Hardened unit mirrors `radar-ingest.service` (NoNewPrivileges, ProtectSystem=strict, empty capability set, RestrictAddressFamilies=AF_INET
  AF_INET6 AF_UNIX, MemoryMax ~128M, no writable paths except its log dir). The process never touches the data directory.
- Privacy: armory data is public-game data, but note terms of use (R0) before the page displays it publicly.

## 10. Risks and open questions
1. **No known enumeration endpoint** (R0): "all characters" may be impossible, or may need realm-by-realm crawling that does not fit the key's quota.
2. API shape, field names, and terms of use are unknown until the user supplies docs.
3. Volume: tens of thousands of characters x gear/talent JSON on a weak laptop SQLite (mitigated by delta skip, caps, snapshot pruning, 30-day retention).
4. Midnight load overlaps the nightly backup cron (`deploy/backup.cron`): schedule check; the timer may need a small offset if they collide.
5. Laptop off at midnight: `Persistent=true` runs it at next boot; the run budget must not collide with daytime use.
6. Confirm D2 (DB access via radar-db internal API) and D3 (env var name exception to the `RADAR_*` policy).

## Results: R5 (2026-11-12, internal/mod/armorysync)
Crawler core on fakes; stdlib only, no go.mod change, imports only `domain`. 97.5% statement coverage; gofmt, go vet, go test -count=1 ./... green (`-race` not run, no cgo).
- Modules may not import each other (architecture test), so armorysync declares its own `Source`, `CharRef`, `Page` (same shapes as armoryclient's). R6 must adapt armoryclient's client (its `ListPage` returns `armoryclient.Page`, a different named type, so a ~10-line adapter is needed) and set `Config.AuthErr = armoryclient.ErrAuth`.
- `Syncer` = `New(Source, Sink, Clock, Config)`; `Run(ctx) (Summary, error)`. `Sink` = ApplyBatch/RecordRun/LastRun (the DB API in R6). Optional `Config.Skipper` (`Skip(ctx, CharRef) bool`) for delta skipping; default none. `Config.Sleep` injectable.
- Resume: last run is resumed (same RunID, cursor, counters) only if `status=running` and `FinishedAt=0` and it started on the same local day (`Config.Location`); otherwise a new run `r<startMs>` starts. The domain has no `interrupted` status, so an interrupted run is persisted as unfinished `running` (that is exactly what makes it resumable) while `Summary.Status` says `interrupted`.
- Checkpoint (RecordRun with cursor and counters) after every successful batch; the cursor moves to the page's `Next` only with its last batch, so a crash replays at most one page. `BatchID = sha256(runID|cursor|index|size)[:16]` hex (size keeps a short prefix batch distinct from a full one); replays are no-ops.
- Budgets: wall clock (default 6h) and requests (0 = unlimited, list and detail both count), permits are taken in page order so a stop leaves a fetched prefix, which is still stored; worker pool (default 3) preserves page order in batches (<=100). Stops end as `partial` with a `Note`. Cancel/SIGTERM: in-flight sink calls complete (context detached), then status `interrupted`, exit 1.
- Errors: auth (detail or list) -> `failed`, error wraps `ErrFatal` (exit 2); poison character -> Failed++, skipped (hidden/notfound characters from the Source are stored as such); list failure or sink failure after retries (default 4 attempts, doubling backoff) or checkpoint failure -> `partial`; any Failed>0 at the end -> `partial`. `Summary.ExitCode()`: ok 0, partial/interrupted 1, failed 2. Notes carry only Source/Sink error text (already key-scrubbed by armoryclient).
- Note: a finished run is never resumed, so a second same-day run is a new run; no-op-ness comes from the store's upsert (second run: Stored 0, Skipped N in the test) and from Skipper once R6 plugs one in.

## Results: R6 (2026-11-12, cmd/radar-armory)
One-shot binary; stdlib only, no go.mod change. Files: `main.go` (run/exit codes/signals), `config.go`, `dbsink.go`, `modules.go` (the only file importing `internal/mod/*`: client adapter and syncer wiring), plus `config_test.go`, `dbsink_test.go`, `main_test.go`. Coverage of the package 92%; gofmt, go vet, go test -count=1 ./... green (`-race` not run, no cgo).
- Structure follows `radar-feed` (small standalone cmd with flags + env), not the core Host: a one-shot tool has no listeners or module lifecycle. Settings: flag > `RADAR_ARMORY_*` env > default (`--base-url`, `--key-header`, `--list-path`, `--detail-path`, `--rate`, `--concurrency`, `--max-requests`, `--max-runtime` 6h, `--db-url` default http://127.0.0.1:8789, `--location` default Local, `--version`). Secrets are env only: `WOW_ARMORY_API_KEY` and `RADAR_ARMORY_DB_KEY`, each with a `_FILE` path variant (plain env wins, value trimmed, file capped at 4 KiB); `--api-key`/`--db-key` (and `*-file`) flags are refused via `core.RejectSecretFlags`. Keys live in `secretVal` (redacts on every fmt verb; `config` has its own redacting String/Format) and the API key is wrapped in `armoryclient.NewSecret` in modules.go. Missing key/URL, bad values, secret flags, an http armory URL: message names the setting, never a value, exit 2.
- `dbSink` (implements `armorysync.Sink` structurally, imports only `domain`): POST `/internal/v1/armory/batch`, POST/GET `/internal/v1/armory/run`, header `X-Ingest-Key` (same as the relay). 30 s timeout per call, request cap 8 MiB (radar-db's default body cap; larger = fatal without sending), response cap 64 KiB, no redirects (3xx = fatal, nothing followed), no proxy, only the configured URL. DB URL must be https, or http only for loopback (127.0.0.0/8, ::1, localhost), no userinfo/query/fragment. Errors are `dbError{Retryable}`: network/timeout, 408, 429, 5xx (503, 507) retryable; other 4xx, redirects, oversize fatal; texts hold a status code or fixed phrase only. GET run 404 = no run yet.
- Limitation: armorysync retries every sink error the same way (Attempts 4, doubling backoff), so a fatal 4xx is retried a few times before the run ends `partial`; the retryable flag is carried in the error for a future syncer that distinguishes. Stdout gets one line: `radar-armory: status=.. run=.. enumerated=.. fetched=.. stored=.. skipped=.. failed=.. duration=.. exit=..` (counts only); the secret-free note and errors go to stderr.

## R9a Results (seed feed)

Context change (user decision R0): the Battle.net Classic profile API has no list-all-characters endpoint, so radar-armory seeds its crawl from data radar-db already holds.

- Contract (fixed, the client codes against it): `GET /internal/v1/armory/seeds?cursor=&limit=` on the internal class, ingest role, answers `{"items":[{"kind":"character","realm":"","name":"Ann"},{"kind":"guild","realm":"R","guild":"G"}],"next":""}`. `limit` 1..500 (default 200), `cursor` opaque (empty starts, at most 256 characters). `items` is always an array; `next` is empty when the feed is done. Order: all characters by (lowercase name, lowercase realm), then all guilds by (lowercase realm, guild); each page holds exactly `limit` items unless it is the last (a non-empty `next` always means a full page).
- Characters: `contacts` of every ruleset whose guid starts `Player-` (pings only accept player guids; the filter is defensive), de-duplicated by (realm_lc, name_lc), names must pass the armory name rule (letters, apostrophe, hyphen, space, at most 24; names with digits are skipped). Realm: the contacts table has no realm column, only `raw` = `Name-Realm` (or `Name` when the suffix is unknown), so realm = text after the first `-` of `raw` if it is a valid realm, else `""` (the client applies its configured default realm). Duplicates differing in case keep the smallest spelling, so output is deterministic.
- Guilds: distinct (realm, guild) of `armory_characters` with `guild != ''`, case-sensitive on guild, realm spelled as the smallest stored one. They appear only once characters were stored by an earlier sync, so the first nightly run seeds characters only.
- Code: `domain/armory_seed.go` (types, `ArmorySeed.Validate`, limit and cursor validation, `ArmoryRealmFromRaw`, and `BuildArmorySeedPage`, the one place that implements cursor and page-boundary rules for both stores); optional `core.ArmorySeedStore`; memstore and sqlstore (reader pool, bound parameters, cursor validated by the domain before any query; lazyStore forwards); writeapi route `armory/seeds` (strict query: only `cursor` and `limit`, each at most once, malformed or hostile values 400 `invalid_request` without echoing input and never reach the store; 404 `not_found` when the store lacks `ArmoryStore` or `ArmorySeedStore`; `Cache-Control: no-store`; audit reason `armory_invalid` as the other armory routes). Cursor shape is internal (`c|name_lc|realm_lc`, `g|realm_lc|guild`); clients must treat it as opaque.
- Tests: domain (cursor round trip and rejects, limits, seed validation, realm from raw, paging), storetest contract cases (players only and de-dup, empty store, pagination at every limit covers everything exactly once, characters before guilds, bad cursor and limit => ErrInvalid) run against memstore and sqlstore, sqlstore injection corpus extended to the cursor, writeapi httptest (wire shape, defaults, auth, method, public class 404, hostile cursor and limit, 404 without the interface).
- No schema change, no migration, no go.mod change. NOT RUN: a feed over a real production-size contacts table (the character query reads all rows of one name group and scans forward past skipped names; it is O(contacts) per page worst case, fine for tens of thousands of contacts).
